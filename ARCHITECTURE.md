# Gakuji Architecture

A map of what lives where and why. This describes **roles**, not current
values — it says what a file is *for*, not what's in it right now. Values
change constantly and would make this doc wrong within a week; roles change
rarely. When you add a new file or change what a file is fundamentally *for*,
update this doc.

## The shape of the app, in one paragraph

Gakuji is a Flutter app for studying Japanese: three tabs (Home / Dictionary /
Library) plus per-deck study flows (reading flashcards, kanji handwriting, and a
hybrid mode), a spaced-repetition review system, kana/kanji learning pages,
camera OCR for looking up text from photos, CSV/text term import, and a few
word/kanji games. Sign-in is Google + Firebase Auth (with an anonymous "guest"
session); user data is local-first (SharedPreferences + on-device SQLite) and
syncs to Firestore in the background.

Guiding rule for placement: a file belongs in `core/`, `domain/`, or `data/`
only when **two or more features** use it. Otherwise it lives inside the one
feature that uses it. Features may import each other; `core/`, `domain/`, and
`data/` must not import from `features/`.

## The Term/Deck relationship — the one genuinely tricky part

The real dictionary (served via `DictionaryService`) is the canonical, global
list of words — one `Term` per unique dictionary entry. These are never meant
to be mutated.

When a word gets saved into a deck, `Term.deckCopyFrom(...)` creates an
**independent copy** with a brand-new `id`, while `sourceId` keeps pointing back
to the original dictionary term's id. This is why:

- Marking a card as starred, or editing its note, in one deck never affects the
  dictionary original or the same word saved in a *different* deck — each save
  is its own copy.
- Code can still answer "is this dictionary word saved anywhere?" by comparing
  `sourceId`, without decks holding shared references to the same object.
- `Deck.terms` always holds these deck-owned copies — never a direct reference
  into the dictionary.

If something about save/star/note behavior seems confusing, this copy-on-save
split is almost always the reason.

## The dictionary pipeline

`assets/dictionary/dictionary.db` is a pre-built SQLite database bundled with
the app — it is **not** built at runtime. It's generated offline by Python
scripts in `tools/`, primarily `convert_jmdict_to_sqlite.py`, which parses
`tools/source/JMdict_e.gz` (a gzipped XML dump of
[JMdict](https://www.edrdg.org/jmdict/j_jmdict.html)) into the schema
`DictionaryService` expects. The other `tools/debug_*.py` and
`check_priority_row.py` scripts are one-off debugging aids.

The `.db` file is gitignored (download it from Releases or regenerate it). CI
and local test runs `touch` an empty stand-in so the asset-bundle check passes.

**Gotcha:** `DictionaryService.dictionaryDatabaseFileName` is a versioned
filename (`dictionary_v7.db` at time of writing). Bump the version whenever you
regenerate the asset — the app copies the bundled DB into permanent on-device
storage on first run, so without a version bump a device keeps using its stale
extracted copy forever.

## Imports

All intra-package imports use `package:gakuji/...` (enforced by the
`always_use_package_imports` lint), never relative paths — so moving a file only
changes that file's own import line.
